### 搞懂 runtime GEMM 呼叫鏈：`hipblasLtMatmul` 如何一路走到 kernel launch

- From hipblasLt to Kernel launch
  - See [runtime-flow.md](../hipblaslt/runtime-flow.md)
  ```mermaid
  flowchart TD
      A["hipblasLtMatmul"] --> B["rocblaslt_matmul / _impl"]
      B --> C["建立 RocblasltContractionProblem (訂單)"]
      C --> D["runContractionProblem (派工總管)"]
      D --> E{"有指定 algo 嗎?"}
      E -->|"沒有"| F["getBestSolutions：跑 heuristic 選一個"]
      E -->|"有"| G["用 algo 裡帶的 solution index"]
      F --> H["getSolutionByIndex 取出 solution"]
      G --> H
      H --> I["solution->solve()：產生 kernel 呼叫參數"]
      I --> J["launchKernels：lazy 載入 .co 並執行"]
  ```


  1. **Stage1: API entry point**
    - 程式碼：[hipblasLtMatmul](../../projects/hipblaslt/library/src/amd_detail/hipblaslt.cpp#L521)
      - `hipblasLtMatmul()` API being called
      - Args including problem def & device, env info
  2. **Stage2: Wrapping the problem args**
    - 對外 wrapper：[rocblaslt_matmul](../../projects/hipblaslt/library/src/amd_detail/rocblaslt/src/rocblaslt_mat.cpp#L713)
      - Call `rocblaslt_matmul()` for verification & problem size fetching
      - Using designed format to describe the problem (`RocblasltContractionProblem`)
      - same args as `hipblasLtMatmul()`
    - 核心實作：[rocblaslt_matmul_impl](../../projects/hipblaslt/library/src/amd_detail/rocblaslt/src/rocblaslt_mat.cpp#L44)
      - Call `rocblaslt_matmul_impl()` with the problem
      - arg using `RocblasltContractionProblem`
  3. **Stage3: Assign the task to Tensile**
    - 派工總管：[runContractionProblem](../../projects/hipblaslt/library/src/amd_detail/rocblaslt/src/tensile_host.cpp#L3235)
      - **Tensile Host** in charge using `runContractionProblem()` 
        - args using `rocblaslt_handle`, `rocblaslt_matmul_algo` (if designated sol provided), `RocblasltContractionProblem`, `gemmData` (using shared ptr)
    - 更新 problem：[updateTensileProblem](../../projects/hipblaslt/library/src/amd_detail/rocblaslt/src/tensile_host.cpp#L2086)
      - `updateTensileProblem(prob, tensileProblem)` then translate `RocblasltContractionProblem` into `tensileProblem` format, so that it can be used for lookup table & `solve()`
  4. **Stage4: Choose kernel base on matrix size**
    - codebase:
      - heuristic 排序：[getBestSolutions](../../projects/hipblaslt/library/src/amd_detail/rocblaslt/src/tensile_host.cpp#L4316)
      - 條件樹比對：[ExactLogicLibrary::findTopSolutions](../../projects/hipblaslt/tensilelite/include/Tensile/ExactLogicLibrary.hpp#L264)
      - 依 index 取 solution：[MasterSolutionLibrary getSolutionByIndex](../../projects/hipblaslt/tensilelite/include/Tensile/MasterSolutionLibrary.hpp#L210)
    - Using designated algorithm (if have) for specific solution
    - If no designated algorithm, choosing solution base on heuristic method
    - 真正比對矩陣大小的「查表」邏輯，在 TensileLite 的 library logic（一棵依條件分層的樹）。
  5. **Stage5: Lazy load and launch kernel**
    - codebase:
      - 展開成 kernel 呼叫：[ContractionSolution::solve](../../projects/hipblaslt/tensilelite/src/ContractionSolution.cpp#L3052)
      - lazy 載入 shard：[MasterSolutionLibrary::loadLibrary](../../projects/hipblaslt/tensilelite/include/Tensile/MasterSolutionLibrary.hpp#L146)
      - 逐 kernel launch（需要時才載入 .co）：[SolutionAdapter::launchKernel](../../projects/hipblaslt/tensilelite/src/hip/HipSolutionAdapter.cpp#L522)
      - lazy 載入實作：[FindCodeObject](../../projects/hipblaslt/tensilelite/src/hip/HipSolutionAdapter.cpp#L279)
      - `hipModuleLoad` 載入 module：[loadCodeObjectFile](../../projects/hipblaslt/tensilelite/src/hip/HipSolutionAdapter.cpp#L100)
    - 選好 solution 後呼叫 `solve()` 產生實際的 kernel 呼叫參數（grid 大小、引數），交給 adapter launch。
    - 為縮短啟動時間，kernel 的機器碼檔（`.co`）是**第一次用到才載入**（lazy load）。
    - 回傳一組 `KernelInvocation`（kernel 名、要用哪個 `.co`、grid/workgroup 大小、引數）。接著交給 adapter：`SolutionAdapter::launchKernel(kernel, stream, startEvent, stopEvent, isKernelLoaded)`：

### B. 選擇表 / `.co` / shard

- **這個條件樹是怎麼設計的？為什麼需要設計條件樹？**
  - **一句類比**：整個選擇表就像一疊**層層的 if 判斷**。runtime 拿著「這次要算的 problem（矩陣大小、型別…）＋ 這張 GPU」從最外層開始問：「符合這個條件嗎？符合就往這條路再往下問，不符合就換下一條。」一路問到底，最後落在「這種情況該用哪個 solution」。這疊分層的 if，就是所謂的**條件樹**。
  - **先看名詞：什麼是** `Predicate`**？**
    - `Predicate` 就是**一個回傳 true/false 的條件判斷函式**，形式像 `predicate(problem, hardware) → 成立 / 不成立`。
    - 例如「GPU 是不是 AMDGPU？」「A 有沒有轉置？」「M 是不是等於 4096？」每一個這樣的問題都是一個 Predicate。
  - **樹長什麼樣**：選擇表在 runtime 是一棵 `ExactLogicLibrary`，內部是一串 `rows`，每個 row = **（一個 Predicate 條件, 一個子 library）**。查表時**依序走每個 row**，只要某個 row 的 Predicate 對「當下 problem + hardware」成立，就**遞迴走進它的子 library** 繼續往下比對——一層一層下去，就形成一棵**依條件分層的樹**。
    - 分層順序（由外而內，先便宜後精細）大致是：
      1. 先用**便宜的條件**過濾：GPU 架構是不是 `AMDGPU`。
      2. 再比對 **problem 屬性**：轉置樣式（transpose，如 NN/NT/TN）、資料型別（fp16/bf16/fp8…）。
      3. 最後才做**尺寸比對**（M/N/K）。
    - 尺寸比對本身又有**優先序（找不到就往下退，即 fallback）**：
      - `EqualityMatching`（tuned 過的精確尺寸，最優先）→ `RangeMatching`（尺寸落在某區間）→ `GridBasedMatching` / `FreeSizeMatching` / `PredictionMatching`（heuristic／預測，通用泛化解）。
  - **具體逐層走訪例子**：假設這次要算的是「fp16、NT 排列、M=N=K=4096」，跑在 MI300X 上：
    ```
    root
    └─(Predicate: arch == AMDGPU?)  ✅ 成立 → 進子 library
       └─(Predicate: dtype == fp16?) ✅ 成立 → 進子 library
          └─(Predicate: transpose == NT?) ✅ 成立 → 進尺寸比對層
             ├─ EqualityMatching: 有 tuned 過 (4096,4096,4096) 嗎? ✅ 命中 → 回傳該精確 solution（結束）
             │   （若沒命中，才往下退：）
             ├─ RangeMatching: 4096 落在某個已調的區間嗎?
             └─ Prediction/FreeSize...: 用啟發式挑一個泛用解
    ```
    - 重點：**只要精確解命中就直接用**，命中不了才一層層退回較通用的比對，這就是「精確優先 + fallback」。
  - **為什麼非得用樹（而不是一張平表）**：
    - (dtype × transpose × size × arch) 的組合會**爆炸**，平表查找是 O(n) 線性掃描，慢；而且平表**無法表達**「先找精確、找不到退區間、再退預測」這種**優先級 + fallback** 的語意。
    - 樹的三個好處：
      - (1) 用**便宜條件先剪枝**（先淘汰整批不符的分支）加速
      - (2) 天然表達 **tuned 精確解優先、否則退回泛用解**
      - (3) 讓 tuned 資料**保持精簡**（只需存真正調過的少數精確尺寸，其餘交給泛化解）。
  - **程式碼位置**：定義在 `[ExactLogicLibrary.hpp](../../projects/hipblaslt/tensilelite/include/Tensile/ExactLogicLibrary.hpp)`（`rows` 結構與 `findBestSolution` / `findTopSolutions` / `getSolutionByIndex` 的走訪邏輯），各種 Predicate 在 `Predicates::Contraction`。這棵樹的內容是 **build-time 由** `LibraryLogic.py` **依 benchmark 結果生成**的。
- `.co` **本身已經是可以跑的 kernel binary 了嗎？**
  - **Ans**: 是。`.co` 是編譯完成的 AMDGPU code object（ELF，內含 GPU 機器碼 + metadata），本身就是「可執行的 kernel 二進位」。但要真的 launch 前，仍需先把它 **載入成 HIP module**（`hipModuleLoad` / `loadCodeObjectFile`）並解析出 kernel 函式符號（`hipModuleGetFunction`），才拿得到可呼叫的 handle。lazy load 就是把「載入到 context」這一步延後到第一次用到時才做。
- **什麼是 shard？**
  - **Ans**: 整張選擇表 + 所有 solution metadata 可能很大，於是被**切成多個較小的子表檔案（shard）**。另有一張 `..._Mapping.dat` 記錄「solution index → 它在哪個 shard」。runtime 只在真的需要某個 solution 時，才載入對應那個 shard（lazy），藉此縮短啟動時間、降低記憶體佔用。一句話：**shard = 被切開的選擇表分片**。



### C. repo 為何長這樣

- **看不懂所謂的「長這樣」定義是什麼？是指 Sparse 還是什麼東西？**
  - **Ans**: 「長這樣」不是指 Sparse，而是指「**這個 repo 的資料夾佈局為什麼是現在這個樣子**」。答案就是被 build-time / runtime 兩階段分工決定的：
    - `tensilelite/`（+ `device-library/`）＝ **建置期**：產生 `.co` 與選擇表 `.dat`。
    - `library/`（公開 API + 內部 `rocblaslt` 派工層）＝ **執行期**：查表、載入 `.co`、launch。
    - 兩者唯一的接點就是磁碟上那批 `.co` + 選擇表。詳細資料夾對照見 [architecture/hipblaslt-layout.md](../architecture/hipblaslt-layout.md)。



### D. 關鍵資料結構 / GEMM 語意

- **為什麼是** `D = Activation(alpha * op(A) * op(B) + beta * op(C) + bias)`**？alpha, beta 的目的是什麼？**
  - **Ans**: 這是通用 BLAS GEMM 的標準形式。你理解的「element 層級 MAC」是對的。alpha/beta 是**兩個純量係數**：
    - `alpha`：縮放矩陣乘積 `op(A)*op(B)` 的結果。
    - `beta`：縮放「原本就存在於輸出位置的舊 `C`」。
    - 常見特例：`beta=0` → 完全忽略舊 C（純 `D = A*B`）；`beta=1, alpha=1` → 把 A*B **累加**到舊 C 上（`D = A*B + C`）。
  - **(1) 為什麼「迭代法／很多演算法」需要 alpha, beta？**
    - 關鍵在於：真實計算裡，**很少只算一次孤立的** `A*B` **就結束**，多半是「一個結果矩陣被反覆更新」。GEMM 之所以把 `alpha`、`beta` 直接做進介面，就是為了讓「**縮放後累加到既有結果**」這個超常見的動作一步完成。舉幾個具體例子你就懂了：
      - **分塊矩陣乘法（tiling / K 切段）**：一個大矩陣乘法 `C = A*B`，其中 K 維很大時會被切成好幾段 `A₁B₁ + A₂B₂ + …` 逐段算、逐段疊加。除了第一段用 `beta=0`（初始化），後面每一段都是 `C ← 1·(AᵢBᵢ) + 1·C`（`alpha=1, beta=1`）。**beta 在這裡就是「保留並累加上一輪結果」的開關**。
      - **迭代法（iterative solver，如 CG、GMRES、power iteration 等）**：這類演算法的核心就是「拿上一輪的向量／矩陣 `x`，做一次矩陣運算，再和舊值加權合成新值」，形如 `x_new ← α·(M·x) + β·x_old`。這裡 `α` 通常是**步長 / 學習率**，`β` 是**保留多少舊狀態（動量、鬆弛因子 relaxation factor）**。所以「迭代」需要 alpha/beta，不是因為矩陣乘法本身需要，而是因為**每一輪都要把新算出來的東西按比例混進舊狀態**——這正是 `αA*B + βC` 的形狀。
    - 一句話：**alpha 決定「這次算出來的東西佔多少權重」，beta 決定「舊結果保留多少」**。有了它們，累加、加權平均、步長更新都能用同一個 GEMM 呼叫表達，不必自己再寫一趟 scale+add。
  - **(1b) 到底什麼時候會真的用到「縮放」（alpha/beta ≠ 1）？「普通 GEMM」不是都 1 嗎？**
    - 先破除一個常見誤會：**「普通 GEMM」其實很少剛好是** `alpha=beta=1`。
      - `alpha=1, beta=1` 只是「不縮放、純累加」（`D = A*B + C`）這**一種**特例。
      - 反而「全新算一個矩陣乘法」最常見的是 `beta=0`（`D = A*B`，直接覆蓋、根本不理會舊 C）。
      - 所以「1」不是預設值，只是眾多取值中的幾個；係數 ≠ 1 是因為**很多演算法的公式本來就帶著係數**。
    - **alpha ≠ 1（縮放乘積結果）的實際場景**：
      - **Attention 分數**：`scores = (Q · Kᵀ) / √d`，那個 `1/√d` 就是 `alpha`。與其算完再多跑一趟去除以 `√d`，不如直接把 `alpha = 1/√d` 交給 GEMM。
      - **量化反量化（dequantization）**：int8 矩陣相乘後，要乘一個 scale 還原成浮點數，那個 scale 就是 `alpha`。
      - **取平均**：要算 `N` 個東西的平均時，`alpha = 1/N`。
    - **beta ≠ 0 且 ≠ 1（加權混合舊值）的實際場景**：
      - **移動平均 / 動量（EMA、optimizer momentum、running mean/var）**：`C ← 0.9·C_old + 0.1·(A*B)`，即 `beta=0.9, alpha=0.1`——把「新算的東西」按比例混進「舊狀態」。
      - **迭代法的鬆弛（relaxation）**：`x ← (1-ω)·x + ω·(…)`，係數就是 `alpha`/`beta`。
    - 一句話：`alpha`**／**`beta` **讓「公式裡的係數」被 GEMM 一步吃掉，不用事後再多跑一趟乘加**；它們是 0 或 1 只是其中幾種常見取值。
  - **(2) 這明明是正常 GEMM，為什麼縮放要「摺進 epilogue」？跟 epilogue 有什麼關係？**
    - 先澄清一個誤解：**epilogue 不是某種特殊模式，它是「任何一顆 GEMM kernel 本來就有的尾段」**。一顆 GPU GEMM kernel 的結構固定是兩段：
      - **主迴圈（main loop）**：每個 workgroup 負責輸出的一個 tile，沿 K 維把 `A×B` 的部分積不斷用 MAC 累加在**暫存器 / LDS** 裡。這一段跑完，暫存器裡拿到的是**還沒縮放的純** `A*B` **tile**。
      - **收尾段（epilogue）**：主迴圈結束後、**把結果寫回 global memory 之前**的那一小段程式。
    - 重點來了：`alpha * (A*B)`、`beta * C`、加 bias、套 activation、型別轉換……這些**收尾運算全部塞在 epilogue 一次做完**，因為它們都必須發生在「**結果正要被寫出去的那一刻**」。而那一刻，資料剛好就在暫存器裡、也正要去讀舊的 `C`——所以最自然、最省的做法就是**在 epilogue 順手做掉**：
      ```
      主迴圈： acc = Σ A*B                       // 純乘積，累加在暫存器
      epilogue： out = alpha*acc + beta*C[tile]  // ← alpha/beta 在這裡
                 out = Activation(out + bias)    // bias、activation 也在這裡
                 （順便做型別轉換，例如 fp32 acc → fp16 輸出）
                 寫回 D[tile]
      ```
    - **各步驟的成本**：
      - `alpha * acc`：`acc` 本來就在暫存器裡，乘一個純量幾乎零成本。
      - `beta * C`：這是唯一會多一次記憶體讀取的部分（要把舊 C 讀進來）。但**如果** `beta=0`**，kernel 會直接跳過讀 C**——省掉整趟讀取，這也是為什麼 `beta=0` 通常比 `beta≠0` 快。
      - bias、activation、型別轉換：資料都還在暫存器、正要寫出，順手做完，全程**只有一趟 global memory 來回**。
    - 為什麼強調「摺進去 = 免費」？因為若**不**在 epilogue 做，你就得：先把純 `A*B` 整塊寫回顯存 → 再啟一顆 kernel 把整塊讀回來、乘 alpha、讀 C 乘 beta、加 bias、套 activation、再寫回。這等於對整個輸出矩陣**多跑一趟 global memory 來回**，而 GEMM 尾段常是**記憶體頻寬受限**的，這趟來回很貴。反之 epilogue 裡做，資料本來就在暫存器、C 本來就要讀，乘兩個純量幾乎不增加成本——這就是「摺進同一個 kernel 的收尾階段，等於免費完成」的意思。
    - 所以「正常 GEMM」和「epilogue」不是兩件事：**正常 GEMM kernel 本身就內含 epilogue，alpha/beta 縮放（連同 bias、activation、型別轉換）正是 epilogue 的職責。**
- `leading dimension` **的定義是什麼？**
  - **一句白話**：矩陣在記憶體裡其實是攤平成「一條線」存的。leading dimension（簡稱 `ld`）就是告訴 kernel：「**在這條線上，往下一欄（或下一列）要往前跳幾個元素**」。
  - **為什麼叫「leading」**：矩陣有兩個維度，一個是「連續存放」的維度（記憶體上相鄰），另一個是「要跨一大步才會到」的維度。`ld` 描述的就是**那個要跨大步的維度**——它是決定記憶體佈局的「主導（leading）」維度，所以叫 leading dimension。
    - column-major（BLAS 慣例，欄優先）：同一欄的元素相鄰，`ld` = 跨到「下一欄」要跳幾個元素。
    - row-major（列優先）：同一列的元素相鄰，`ld` = 跨到「下一列」要跳幾個元素。
  - **具體數字例子**（以 column-major 為例）：假設你**實際配置**了一塊 5×5 的大 buffer（每欄 5 個元素連續存放），但你只想用左上角那個 3×3 的邏輯矩陣：
    ```
    大 buffer（5×5），記憶體其實是一條 25 格的線，一欄接一欄：
    第0欄 | 第1欄 | 第2欄 | ...
    [ a ][ . ]   [ a ][ . ][ . ][ . ][ . ]  ← 這 5 格是第 0 欄
    [ b ][ . ]   [ b ]...
    [ c ][ . ]   [ c ]...
    [ . ][ . ]   [ . ]...   （下面 2 格不屬於 3×3，但實體上仍占位）
    [ . ][ . ]   [ . ]...
    ```
    - 你要的 3×3 矩陣每欄只有 3 個有效元素（a,b,c），但**下一欄的起點在記憶體上要跳 5 格**，因為底層 buffer 一欄就是 5 格。
    - 所以這裡 `ld = 5`（buffer 的欄高），**不是** 3（邏輯矩陣的欄高）。kernel 讀第 j 欄第 i 列的元素時，位址 = `base + j*ld + i` = `base + j*5 + i`。
  - **用途**：它把「**邏輯形狀**（我在算的是 3×3）」和「**實體儲存排列**（底層是 5×5）」解耦。最典型的好處是**對一個大矩陣直接取子區塊（sub-matrix）來運算，完全不用複製資料**——只要把 `ld` 設成大矩陣的欄高就行。
  - **一句話總結**：`ld` = 記憶體裡「跨一欄／一列要走幾格」的步長，通常 `ld ≥ 邏輯上該維度的長度`，用來讓子矩陣直接原地運算。
- `batch_stride` **的影響是什麼？在 GPU 架構上 fetch 資料的速度嗎？**
  - **一句白話**：batched GEMM 是「**一次呼叫就算好幾個矩陣**」（例如一口氣算 8 個 A×B）。這些矩陣一個接一個排在記憶體裡，`batch_stride` 就是告訴 kernel：「**從第 i 個矩陣的起點，要往前跳幾個元素才會到第 i+1 個矩陣的起點**」。
  - **具體數字例子**：假設每個 A 矩陣是 128×128 = 16384 個元素，8 個 A 緊密排在一起，那麼 `batch_stride_A = 16384`。kernel 要讀第 i 個矩陣時，起點 = `base + i × batch_stride` = `base + i × 16384`。所以它本質上是**一個算起始位址用的參數**。（如果矩陣之間有留空隙，stride 就會比 16384 大，用來跳過空隙。）
  - **所以它影響的是「定址」，不是直接決定 fetch 速度**：它讓一次呼叫能正確定位到 batch 裡的每個矩陣，本身不是「加速讀取」的旋鈕。只有當 stride 造成的**存取樣式**影響到記憶體區域性（locality／對齊）時，才會**間接**影響效能——但那是副作用，不是它的用途。
  - **一句話總結**：`batch_stride` = batch 裡「跳到下一個矩陣」的位址步長，管的是**怎麼找到資料**，不是**多快讀到資料**。
- `runContractionProblem` **的疑問**
  - **adapter 的定義：** 
    - `adapter` 指 `[TensileLite::hip::SolutionAdapter](../../projects/hipblaslt/tensilelite/include/Tensile/hip/HipSolutionAdapter.hpp#L45)`，是 **HIP 層的執行代理**：它持有已載入的 code object modules（`hipModule_t`）、維護「kernel 名稱 → `hipFunction_t`」的對應、負責 `.co` 的 lazy 載入（`loadCodeObjectFile` / `initializeLazyLoading` / `FindCodeObject`），並最終發出 `hipModuleLaunchKernel`。
    - 概念上它是**抽象的** `KernelInvocation`**（由** `solve()` **產生）與底層 HIP driver 呼叫之間的橋**，把「裝置端 launch 的機械細節」封裝起來。實作上是 **per-device 快取的單例**（一張 GPU 一個 adapter），由 tensile host 用 `get_library_and_adapter()`（[tensile_host.cpp#L2958](../../projects/hipblaslt/library/src/amd_detail/rocblaslt/src/tensile_host.cpp#L2958)）依 device id 取得並在第一次使用時 lazy 初始化。
  - `rocblaslt_handle` **的定義**: 
    - 是 rocBLASLt 的 **opaque 內部 context/session handle**，承載這一組呼叫共用的狀態：device id、stream、device properties，以及對已載入 library / adapter 狀態的存取。
    - 它是對外 `hipblasLtHandle_t` 的內部對應物；每個 API 呼叫都帶著它，讓 host 知道「這次跑在哪張卡、用哪份 library」。
  - **都有** `prob` **了為什麼** `gemmData` **裡還要包 problem 和 kernel？傳入 algo 代表 kernel 還沒選定？**`gemmData` **裡的 kernel 會被變動嗎？還是這個 pointer 就是拿來被填資料的？**
    - **Ans**: 你的直覺基本正確——`gemmData` 就是一個**傳進來被填 / 被重用的可變工作緩衝**。它的型別是 `[TensileDataGemm](../../projects/hipblaslt/library/src/amd_detail/rocblaslt/src/tensile_host.cpp#L3051)`，欄位有 `problem`（Tensile 格式）、`inputs`、`kernels`、`algoIndex`。要點：
      - `prob`（`RocblasltContractionProblem`）是 **rocblaslt 格式的「訂單」**；`gemmData->problem`（`ContractionProblemGemm`）是**翻譯成 Tensile 格式後的 problem**，兩者不是重複，是**同一問題的兩種表述**，由 `updateTensileProblem(prob, data->problem)` 做轉換。
      - 之所以把它們包在一個持久物件裡，是為了**重用**：hipBLASLt 的 ext API 允許你建立一個 gemm 物件後**重複呼叫**，`gemmData` 讓重複呼叫時不必每次重新翻譯 problem / 重新配置。
      - `kernels` 欄位是**輸出槽**：選定 solution 後由 `solve()` 產生 `KernelInvocation` 填進去，會被（重）寫入——所以是的，它會被變動。
      - 傳入 `algo` 只是**指定要用哪個 solution index**（若為 `nullptr` 就跑 heuristic 選）；真正的 kernel（`.co` / `KernelInvocation`）要到 `solve()` / launch 才展開。所以「傳 algo 時 kernel 尚未實體選定」是對的，`gemmData` 的用途正是被傳進來承接這些結果。
- `epilogue` **的定義是什麼？**
  - **Ans**: GEMM 主乘法之後的收尾運算（加 bias、套 activation、乘 alpha/beta、型別轉換等），通常和主乘法融合在同一個 kernel 尾段執行以省一趟記憶體來回。
- **條件樹比對實際是怎麼做的？「library logic（一棵依條件分層的樹）」能不能更詳細一點？**
  - **Ans**: 見上面 **B 節第一題**的完整說明。簡述：runtime 走 `ExactLogicLibrary::findTopSolutions` / `findBestSolution`，逐一測試每個 row 的 Predicate（`row.first(problem, hardware)`），成立就遞迴進子 library；比對優先序為 精確（Equality）→ 區間（Range）→ heuristic/預測（GridBased / FreeSize / Prediction）。程式碼在 `[ExactLogicLibrary.hpp#L264](../../projects/hipblaslt/tensilelite/include/Tensile/ExactLogicLibrary.hpp#L264)`，取解則靠 `[MasterSolutionLibrary::getSolutionByIndex](../../projects/hipblaslt/tensilelite/include/Tensile/MasterSolutionLibrary.hpp#L210)`。
