依側線切出前最後確認，S10R3 已完成 global 32 chunks，並進入 15 個 conditional targets；當時總進度是 54/512 chunks。它仍在 CPU valid-support discovery，還沒開始 Formocast、GPU correctness 或效能測量。

## 為什麼這個入口檢查有必要？

可以把 YAML 想成「商品目錄」，Ductile validator 則是「實際能不能運作的檢驗」。

YAML 寫著 `DepthU`=1024，只表示：

> 目錄裡列了這個選項。

不表示：

> 一定存在一組其他參數搭配它，而且整個 kernel 設定能通過 Ductile。

S10R1 的核心問題，就是太接近把「目錄裡有」當成「實際可用」，並要求 exact-ten corpus 強制包含 YAML 的極端值。

結果固定 DepthU=1024 後，超過百萬 draws 仍沒有 accepted config。

如果忽略這個問題，直接進入 S11，後續研究可能得到完全錯誤的結論：

- 把實際上幾乎無法形成 valid config 的值交給 Formocast guidance；
- 將 mapping failure 誤認為模型失敗；
- 將 YAML candidate frequency 誤認為 operational sampling mass；
- 用人工挑選的少數容易成功 config，誇大 factorized guidance 的效果；
- 後續 S11–S41 即使花更多 GPU 時間，也建立在不可信的入口資料上。

因此 S10R3 現在先回答一個更基礎的問題：

> 在真正通過 Ductile validator 的完整 joint configs 裡，哪些 candidate values 至少有 fresh witness？

這相當於先確認「研究對象真的存在」，才開始研究模型能不能引導它。

## 為什麼不能找到幾個 valid configs 就停？

因為這會造成結果驅動的停止。

例如：

- 某個值很快找到 witness 就停止；
- 某個麻煩值一直找不到就提早放棄；
- 看到足以組成漂亮 mapping corpus 就停止；
- 發現結果可能不利，就追加更多 draws。

這些做法都會讓樣本量和結果互相影響。最後無法判斷 corpus 是 protocol 產生的，還是研究者看到結果後挑出來的。

所以 S10R3 在第一筆 draw 前就固定：

- global：32 × 512 = 16,384 draws；
- 最多 15 個 conditional targets；
- 每個 target 固定 32 × 512 = 16,384 draws；
- 不 early-stop、不追加；
- 最多總計 512 chunks／262,144 draws。

global 最後確實啟用了全部 15 個 targets，因此這次會走完整上限。這不是執行途中擴張實驗，而是事先鎖定的最壞情況真的發生了。

## 這 15 個 conditional targets 帶來什麼價值？

global sampling 已找到：

- 34 個 accepted occurrences；
- 34 個 distinct valid configs；
- 123 個 witnessed candidate atoms。

但仍有 15 個高優先候選沒有 witness，包括 DepthU=1024。conditional stream 會固定其中一個值，再抽其他完整參數，回答：

> 這個值沒有在 global 中出現，是因為 global 樣本不夠，還是它在 valid support 裡真的極罕見？

即使 16,384 次仍為零，也不能宣稱「不存在」，但可以形成一個可信、可重現的結論：

> 在這個預先鎖定的 conditional sampling law 與 cap 中，沒有觀察到 valid witness。

這比「我試過很多次都不行」強很多，因為它有固定：

- sampling law；
- seed；
- draw count；
- validator；
- rejection taxonomy；
- complete config identities；
- ledger replay。

它能支持後面的 guidance eligibility 判斷：有 unobserved/proven-absent value 的整個 gene 不進 S11 guidance，但不擅自從 YAML search space 刪掉該值。

## 為什麼實際執行比原估慢這麼多？

這部分要坦白：是 throughput 估計失準，不是科學問題本身突然變大。

原 frozen estimate：

- wall：約 12,669 秒，約 3.5 小時。

前 6 chunks 實測：

- 3,072 draws；
- 676.9 秒；
- 約 4.54 draws/秒；
- 推估 512 chunks 約 57,761 秒，也就是約 16 小時。

實際速度約比規劃慢 4.5 倍。

原因是每個 512-draw chunk 不只是跑一次簡單條件判斷。它還要：

1. 依 actual YAML 產生 512 個完整 joint configs；
2. 建立 pinned Ductile/Tensile 驗證環境；
3. 初始化 gfx942、assembler、global parameters 與 BenchmarkProcess；
4. 對每個 config 呼叫真正的 _validate_solution；
5. 保存 request、stdout、stderr、config、hash 與 validation；
6. 寫成約 1 MB 的 atomic chunk；
7. 更新 digest-chained ledger。

實測中 validator child 本身約數秒，但一個 chunk 端到端接近兩分鐘，表示主要瓶頸在完整 config generation、初始化與逐 chunk orchestration。這應該在正
式 lock 前，用相同程式做更準確的 1% workload benchmark；當時估計沒有充分捕捉這部分成本。

因此：

- workload 沒有失控；
- process 沒有 hang；
- storage 甚至低於預估；
- 但 wall-time 規劃確實做得不夠好。



## 為什麼前面還做了 18 輪 repair？

這 18 輪不是做了 18 次科學實驗。絕大多數發生在正式 evidence 前，是在修執行與治理問題，例如：

- implementation 還綁定舊 Plan-B ID；
- 新 freeze 的欄位層級讀錯；
- visibility fields 被放進不存在的 wrapper；
- sentinel threshold fixture 與 native semantics 不一致；
- unrelated working-tree drift 被錯當成實驗 blocker；
- repair count 被錯當成硬性停止上限；
- lock、contract、implementation 與 registries 的 exact hashes 沒有完整閉合；
- post-commit audit 與 effective-lock admission 尚未對齊。

這些修復最後帶來的價值是：

- 正式 evidence 使用的確實是核准過的程式 bytes；
- runner、contract、registry、fixture、native helper 都有 hash binding；
- 沒有人能在看到結果後換 implementation；
- auditor 能重播並驗證每個結論；
- S10、S10R1、S10R2 與 S10R3 的 evidence 不會互相污染。

但必須承認：不是每一輪都值得發生。多輪 repair 反映了早期 integration coverage 和治理設計不足。幾個問題本來可以透過「直接對真實 freeze 做整合測試」
一次抓出，而不是連續修 V2 ID、欄位層級和 wrapper。

所以這部分的正確評價是：

> 最終閉合的 lock/audit 有價值；造成 18 輪才能閉合的過程，部分是可避免的工程成本。



## 目前花的時間最後換到什麼？

最主要有六項價值：

1. 保護後續研究結論

防止 S11–S41 建立在非法、極罕見或人工挑選的入口設定上。
2. 把「候選存在」與「valid support」分開
特別是 DepthU=1024，不再用 YAML declaration 或 stochastic zero 偷換成 support 結論。
3. 建立 guidance eligibility
哪些 genes 有完整 witnessed support、哪些必須維持 baseline sampling，將有正式依據。
4. 減少後續 GPU 浪費
CPU 先過濾入口問題，避免花更多 GPU 時間生成、編譯及測量根本不可信的 mapping corpus。
5. 讓 negative 結果也可解釋
後續失敗時可以區分：

- mapping failure；
- correctness failure；
- noise instability；
- support 不完整；
- harness defect。

1. 形成可公開辯護的 claim boundary

最後可以誠實說明研究回答了什麼，以及沒有回答什麼；不會把「沒抽到」說成「不存在」，也不會把入口 gate 誇大為模型有效性證明。

## 我的直白判斷

有必要的部分是：

- support-aware 三態分類；
- 預先鎖定的 sampling schedule；
- deterministic conditional target selection；
- effective lock 與獨立 audit；
- mapping/native/GPU correctness/noise 分離；
- S10 immutable、舊 evidence 不混用。

不應再重複的部分是：

- 用百萬級 stochastic search 強迫 nominal extreme 進 corpus；
- 在真實 freeze 整合測試不足時反覆修 identity adapter；
- 把無關 worktree drift 當實驗 blocker；
- 先鎖 3.5 小時估計，卻沒有用相同正式路徑測出每 chunk 約兩分鐘；
- 對普通 repair 建立過多人工中斷點。

因此，這次 S10R3 的完整 run 可以視為一次性的「入口地基驗收」。它的成本值得，是因為後面還有 S11–S41；如果地基錯了，後面更昂貴的 GPU 實驗全部會失去
解釋力。
但這不代表未來每個 checkpoint 都應該這麼重。這次留下的 validator、registries、ledger、lock/audit 流程和實測 throughput，真正的長期價值應該是讓後續
checkpoint 不再重走同樣的 18 輪修復與錯誤估時。
